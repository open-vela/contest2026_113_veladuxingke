# R528 板载音频与首阶段语音闭环开发记录

## 1. 范围与边界

本阶段恢复 DshanPixVela-Devkit 的板载 DMIC 和扬声器通路，并在 `routine_mgr` 中加入“点击开始/停止 → 录音 → 温度屏显 → 提示音和中文播报”的应用架构。

当前仓库没有许可明确、可直接部署的中文 KWS 模型。因此本阶段识别后端只做有效人声检测，检测成功后映射到唯一演示命令“现在温度多少”；界面始终显示“演示识别：未验证语义”。这不能作为中文命令识别完成的证据。

## 4. 应用架构

新增模块：

- `audio_service.c/.h`：独立 pthread、录放音、取消、generation 防旧结果覆盖、状态快照；
- `voice_recognizer_demo.c`：按 20 ms 帧检测峰值与 RMS，只判断是否存在有效人声；
- `voice_reply.c`：把 `temperature_x100` 转为中文数字片段并生成单个 `/tmp/routine_reply.pcm`；
- `tools/prepare_voice_assets.py`：验证母版 WAV，转为 16 kHz/16-bit dual-mono PCM，并生成来源、许可证 URL 和 SHA-256 清单。

状态机：

```text
IDLE -> LISTENING -> PROCESSING -> SPEAKING -> IDLE
                             \-> ERROR
```

LVGL 点击回调只发起 begin/cancel；录音停止、VAD、文件拼接、播放和线程 join 均不在 LVGL 回调中执行。现有 1 秒环境 timer 将融合后的当前温度复制给音频服务，100 ms voice timer 只复制状态快照并更新界面。

### 6.3 连续播报 lifecycle 失败镜像与 RAMP W1C 修复（2026-08-11 至 2026-08-12）

#### 真机反馈与根因边界

在传感器数据语音正在播放时，如果注意事项到期，会出现提醒弹窗；但传感器自然播放结束后，提醒没有语音，随后传感器数据播报也可能继续无声。串口能看到当前片段完成和 PCM close：

```text
playback final buffer complete
playback exit
sunxi_audio_stop
snd_vela_pcm_close
```

同时出现的三条 `AUDIO_TYPE_FEATURE / Unrecognized feature unit` 分别是 NxPlayer 尝试 balance、bass、treble，而 R528 lower-half 只支持 volume。它们后面仍能看到当前片段自然完成，因此属于能力噪声，不作为本次连续无声的根因。

源码排查确认：

1. due popup 和 reminder audio 是独立队列，popup 先出现只证明 UI 接收了 occurrence；
2. reminder 在传感器播放期间会保留，但旧 worker 在完成后先公开 `IDLE`，新 foreground request 可越过等待提醒；
3. reminder 原先在构建/播放成功前就破坏性出队，底层失败后不会重试；
4. R528 playback worker 自然完成时先 `file_mq_close()`，之后 COMPLETE 触发 NxPlayer STOP，STOP 又向已关闭 MQ 发送；当前 debug 固件会返回并忽略 `-EBADF`，非 debug 路径存在空 inode 解引用风险；
5. NxPlayer 的 `IDLE` 早于 playthread 真正退出，wait、join、release、线程自释放和 startup error unwind 没有清晰的单一 owner。

#### 修复内容

- `audio_service` 使用不可变 operation snapshot；worker 在同一把锁内按“当前 operation 完成 → due reminder FIFO → pending foreground”认领下一项，不再暴露提醒切换前的中间 `IDLE`；
- reminder 保留 `(schedule_id, sequence)` 精确身份，首次基础设施播放失败会有界重试一次，完成/延后/关闭只取消 matching occurrence；
- snapshot 增加 operation ID、pending reminder 数和当前 reminder；UI 在其他音频占用时稳定显示 busy，不再让按钮看似接受后静默无声；
- NxPlayer 新增 `nxplayer_wait()`，playthread 只执行私有 ref-put，外部 wait 是 join owner；STOP 在 mutex 外执行有界 MQ send，startup failure 会回收 reservation、MQ、thread ref 和设备 FD；
- R528 playback worker 不再关闭控制 MQ；自然 completion 不向已退出 worker 发送 STOP，由 stop/start-error 统一回收 task、PCM、MQ 和同步对象；自然 EOF 继续 drain，用户 stop 继续 drop；
- 增加 operation claim/finish/retry 串口诊断，并新增 6 项 audio lifecycle host 契约及 firmware selftest 的 reminder-priority 检查。

#### 失败镜像真机复验与最终根因

2026-08-11 已烧录本节 lifecycle 镜像（NuttX `4ec5dc6a58ad694a1be524bb0fa55911b0f9a040c5a3b97b2c7e57c2dc328c28`，NAND `6df8abca8bec181a5c26a46d9b7b5787e32737b7e5e3be23f84165e893664e8f`），并再次稳定复现：首段传感器有声，提醒入队后当前段自然完整结束，此后提醒及所有传感器均无声。它是**已复现缺陷的失败镜像**，不再是“尚未烧录候选”。

新日志证明上述 application/NxPlayer/lower-half 修复均正确：`sensor finish → reminder claim` 原子切换成立；每段重新 open/configure/start；PA GPIO 为高，DAC 数字/模拟与 unmute 位正常，`DAC_CNT` 持续增长。无声边界最终收敛到 R528 Codec：

```text
首次有声 hp-on:       ramp=0x40180001
关闭后 hp-off:        ramp=0x00180000
后续已送样但无声:     ramp=0x00180001
chip=3:               non-A RDEN 路径
```

T113/R528 手册确认 `SUNXI_RAMP_ANA_CTL` 是混合访问寄存器：bit 30 `RAMP_RISE_INT`、bit 28 `RAMP_FALL_INT` 为 R/W1C completion，bit 1 `RMCEN`、bit 0 `RDEN` 为普通 R/W。通用 `snd_codec_update_bits()` 会无意回写状态位；但 2026-08-12 首版仅禁止回写仍然失败：真机读回 `0x40180001 → 0x40180000 → 0x40180001`，rise completion 持续 pending。另确认 `snd_writel` 是赋值宏，`snd_codec_write()` 的 `1572865/1572864` 正常返回值就是 `0x00180001/0x00180000`，不是 errno。

当前修复将普通控制与显式 W1C acknowledgement 分离，启动前清旧 completion，按 Tina Linux non-A 顺序执行 `RMCEN=0 → RDEN=1 → wait/ack rise`；关闭执行 `RDEN=0 → wait/ack fall → DAC off`；route 5 关闭改为 HP 后 lineout，lineout 仅在 `RDEN=0` 时控制 `RMCEN`。不使用 Codec reset 或 PA 脉冲掩盖问题。

关键日志格式：

```text

routine_mgr: audio claim op=<op> request=<type> reminder=<id>/<sequence> pending=<n>
routine_mgr: audio finish op=<op> outcome=<result> error=<code> pending=<n>
routine_mgr: retry reminder=<id>/<sequence> error=<code>
```

本次确认范围是实际复现链路中的传感器 → reminder → 延后 reminder → 后续传感器均有声，足以关闭连续播放无声缺陷。此前 MiMo 固定温度播报验收与两版失败镜像历史均继续保留。未单独声明通过的 20 轮压力切换、真实中文 KWS、50 次连续交互和长期稳定性仍不得推断为完成。

## 8. 中文离线 KWS 语料阶段（2026-08-12）

当前已按“先采集真实 R528 DMIC 数据，再训练小型全 INT8 模型”的路线开始开发。新增 KWS 采集早期退出模式：它在 `lv_init()` 和正常 `audio_service` 之前运行，只录制 `/dev/audio/pcm1c` 的 16 kHz/16-bit/mono PCM，不启动屏幕、传感器、播报或 demo recognizer；正式样本和 JSON sidecar 持久写入 `/data/kws_corpus`，采用 `.part` 加 hard-link no-replace 发布，避免覆盖已有语料。首轮真机反馈发现 `CONFIG_NSH_LINELEN=64` 且 NSH 不把 `\` 当作跨行续写，长选项被截断；后续固件新增 `-K/-l/-p/-s/-i/-n/-m` 短选项，真机使用 59 字符单行命令 `routine_mgr -K -l query_temperature -p s001 -s smoke_a -n 1`。第二轮诊断日志确认 YAFFS 可用 72,351,744 bytes，但 sample 路径预检误报 `no unused take/-28`；根因不是空间，而是原始长文件名超过 `CONFIG_NAME_MAX=32`。现改为 `k<16hex>_<2位label>_<4位take>` 紧凑 ID，完整上下文继续保存在 JSON sidecar，并增加 NAME_MAX 契约测试。第三轮真机已进入交互和 `3/2/1`，但录音创建返回 `-36/ENAMETOOLONG`；继续确认正式名虽已合规，旧 `.sample.pcm.part-<pid>` 临时名仍超限。现同步改为不超过 15 字符的 `.p<pidhex>.<take>`/`.j<pidhex>.<take>`，保留 O_EXCL 和取消清理语义。第四轮真机已成功录制两次 114,688 bytes/3584 ms，peak 分别为 7873/9476，证明 DMIC 和临时 PCM 正常；保留阶段返回 `-2/ENOENT`，根因是 `CONFIG_FS_LINKS` 未启用而发布逻辑依赖 `link()`。现改为目标双重预检后同 YAFFS rename，并在 JSON 失败时回滚 PCM；同时按用户要求在指标计算后自动用 `/dev/audio/pcm0p` 回放临时录音，试听后再选择保留或重录。

主机侧已新增确定性 importer 和可选 MiMo-V2.5-ASR baseline：importer 校验样本配对、格式、时长和元数据，原样保留 PCM并生成 payload 一致的 WAV、SHA 和声学指标；MiMo 工具只在用户逐项选择录音、确认上传并安全输入 API key 后运行，不进入固件也不改变人工标签。新增 23 项测试后完整 host suite 为 81 项通过。

该阶段已完成候选固件构建和 NAND pack（NAND SHA-256 `e85f915b91d922d68afc809ec8f6e5827fa7e7cb0ebe456e29b95deaa4f34a99`），但尚未烧录、采集真实语料、调用真实 MiMo API或训练/接入 TFLite Micro。因此现有运行后端仍是 `voice_recognizer_demo.c`，不得把上述代码、主机测试或打包结果写成中文语义识别已完成。详细命令、隐私边界、状态表和真机步骤见 [`中文离线语音识别开发与验收记录.md`](中文离线语音识别开发与验收记录.md)。
